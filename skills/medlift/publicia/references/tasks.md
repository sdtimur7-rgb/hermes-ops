# Задачи: контроль исполнения

С 24.09 задачи сотрудникам заводит **движок платформы** — по событиям и состояниям:
клиент ждёт ответа, оплата не прошла, клиент оплатил и нужен онбординг. Ответственного
он назначает сам, срок ставит по SLA типа, просрочку эскалирует.

Ты здесь **внешний контролёр**: читаешь, сверяешь, рекомендуешь, зовёшь людей.
Закрыть, переназначить или перенести задачу нельзя — таких ручек нет, это не вопрос
прав. Изменить правила движка (SLA, пороги, получателей эскалаций) — только заявкой
`POST /actions/propose`.

## Ручки

| Ручка | Право | Журнал | Что отдаёт |
|---|---|---|---|
| `GET /tasks` | `data:read` | да | `{items, next_cursor, has_more}`, новые первыми |
| `GET /tasks/{id}` | `data:read` | да | `{task, history[]}` |
| `GET /tasks/sla-violations` | `data:read` | да | задачи людей с нарушенным сроком |
| `GET /tasks/metrics` | `data:read` | да | `{period, metrics}` |
| `POST /tasks/{id}/annotations` | `tasks:write` | да | рекомендация или разбор к задаче |
| `POST /tasks` (= `/actions/create-task`) | `tasks:write` | **нет** | задача вручную; дедупликация только полем `externalKey` |

«Журнал» — как в `endpoints.md`: лимиты, `X-RateLimit-*`, `Idempotency-Key`,
`GET /audit-log`. Проверено на живом API 25.09: аннотации идут новым обработчиком,
`POST /tasks` — старым.

## GET /tasks

Параметры: `state` = `active` (по умолчанию) | `overdue` | `completed` | `cancelled` | `all`;
`type`; `assignee_id` (id из `GET /employees`); `deal_id`; `client_id`; `due_before` и `since`
(ISO-8601); `status`; `limit` (до 200, по умолчанию 50); `cursor`.

- **Без `state` приходят только открытые** — так с 24.09, раньше приходили любые.
  Нужно всё — передавай `state=all`.
- `client_id` в ответе — псевдоним, а фильтр `?client_id=` ждёт настоящий id.
  Задачи клиента ищи по `deal_id`.
- В список попадают и задачи ИИ-исполнителей. Метрики и нарушения SLA считают
  только задачи людей — поэтому числа списка и метрик могут не совпадать.

## Форма задачи

Одна и та же в `GET /tasks`, `GET /tasks/{id}` и `GET /tasks/sla-violations`.

| Поле | Смысл |
|---|---|
| `type` | тип автозадачи (таблица ниже); `null` — задачу завели вручную или через `POST /tasks` |
| `state` | `OPEN`, `IN_PROGRESS`, `ESCALATED` (срок прошёл, просрочка поднята, задача открыта), `COMPLETED`, `CANCELLED` (повод исчез до выполнения) |
| `priority` | у автозадач `NORMAL`, `HIGH`, `CRITICAL` |
| `title`, `action` | что случилось и что сделать |
| `assignee` | `{id, name}`; без `pii:read` имя — роль и инициал |
| `deal_id`, `conversation_id`, `client_id` | куда идти за контекстом; `client_id` — псевдоним |
| `due_at` | срок именно этой задачи — его и сравнивай, а не SLA из таблицы |
| `escalation_level`, `last_escalated_at` | уровень эскалации 0–3 и когда поднят |
| `completion` | `{rule, trigger, event_id, outcome}` — как задача закроется сама и что её закрыло |
| `links` | адреса админки для человека: тебе по ним не пройти, нужен вход сотрудника |
| `status`, `done` | внутренние поля для совместимости — не опирайся на них |

`completion.rule`: `outbound_sent`, `manager_contact`, `checklist`, `manual`.
`completion.outcome`: `RECOVERED` или `NOT_RECOVERED` у платёжных задач (оплата пришла /
повторный отказ или 7 дней без оплаты), `COMPLETE` у онбординга.

**`title` зависит от `pii:read`.** Без этого права он обезличен, с ним — настоящее ФИО
клиента («… ждёт ответа»). В Telegram, заметки, инциденты и предложения ФИО не
переносить: ссылайся на сделку по `deal_id`.

## Типы автозадач

| `type` | Когда создаётся | SLA | Приоритет | Чем закрывается сама |
|---|---|---|---|---|
| `CLIENT_REPLY_OVERDUE` | клиент ждёт ответа дольше 15 мин, а нужен человек; если сделку ведёт ИИ — после 30 мин тишины и только когда ИИ не готовит ответ | 15 мин | HIGH | любым ответом клиенту |
| `PAYMENT_ABANDONED` | клиент получил ссылку и не оплатил | 10 мин | HIGH | сообщением менеджера клиенту |
| `PAYMENT_FAILED` | провайдер отклонил оплату | 10 мин | HIGH | сообщением менеджера клиенту |
| `INSTALLMENT_REJECTED` | отказ в рассрочке | 10 мин | HIGH | сообщением менеджера клиенту |
| `FOLLOWUP_OVERDUE` | просрочена задача менеджера или застрял follow-up ИИ | 30 мин | HIGH | любым ответом клиенту |
| `CLIENT_ONBOARDING` | клиент оплатил | 24 ч | NORMAL, при просрочке CRITICAL | чек-листом: профиль, данные, статья, инструкции |
| `SYSTEM_OWNER_UNRESOLVED` | движок не нашёл ответственного | 60 мин | CRITICAL | только вручную |

SLA — значения по умолчанию, владелец меняет их в `/admin/tasks-engine`.

**Одна активная задача каждого типа на сделку.** Повторный сигнал вторую не создаёт,
пока первая открыта. Поэтому прежде чем заводить `POST /tasks` по сделке, проверь
`GET /tasks?deal_id=…`: если движок уже ведёт этот повод, твоя задача только собьёт
менеджера.

## Эскалация просрочки

Срок прошёл — событие `task.overdue`. Дальше уровни, каждый с событием `task.escalated`:

- **L1** — повтор ответственному сразу;
- **L2** — через 30 мин операционному руководителю;
- **L3** — через 120 мин основателям, только для HIGH и CRITICAL или если у ответственного
  за сутки уже три эскалированные просрочки.

L3 **уже** дошла до основателей силами платформы. Твоя работа на этом уровне — не
продублировать сигнал, а объяснить причину.

## События task.*

Payload в camelCase. Id задачи — `payload.taskId`, сделка — `related.deal_id`.
Формы ниже сверены с живой лентой 25.09, кроме помеченных.

| Тип | Поля payload |
|---|---|
| `task.created` | задачу завёл человек, ИИ по просьбе клиента или автоматизация; форма payload не сверялась |
| `task.assigned` | `taskId`, `type`, `priority`, `dueAt`, `assigneeId`, `assigneeName`, `title` |
| `task.overdue` | `taskId`, `dueAt`, `title` |
| `task.escalated` | `taskId`, `escalationLevel`, `assigneeId`, `title` |
| `task.completed` | `taskId`, `completedAt`, `completionTrigger`, `completionEventId`, `title` |
| `task.cancelled` | повод исчез до выполнения; форма payload не сверялась |

**Объём большой.** За первые полтора дня после включения движка — больше 200 событий
`task.*`, из них почти сотня просрочек и эскалаций в сутки. Реагировать на каждое
по отдельности нельзя: это завалит людей уведомлениями о том, о чём платформа им
уже сказала. Разбирай уровень 3 и повторы, остальное — в суточный отчёт.

## GET /tasks/{id}

`{task, history[]}`. `history` — по возрастанию времени, до 200 записей, запись
`{id, type, at, payload}`, `payload` обезличен. Типы: `TASK_CREATED`, `TASK_ASSIGNED`,
`TASK_REASSIGNED`, `TASK_OVERDUE`, `TASK_ESCALATED`, `TASK_COMPLETED`, `TASK_CANCELLED`.
Нет задачи — `404 task_not_found`.

## GET /tasks/sla-violations

Задачи людей с нарушенным сроком: `sla_state` = `active_overdue` (срок прошёл, задача
открыта) или `completed_late` (закрыта позже срока), плюс `overdue_minutes`.

- Окно `from`/`to` считается **по сроку** (`due_at`), а не по дате создания;
  по умолчанию последние 30 дней.
- В окне читается до 500 кандидатов — длинный период режь на окна короче.
- `cursor` — id последней задачи страницы.

## GET /tasks/metrics

Параметры `from`, `to` (по умолчанию последние 30 дней), `assignee_id`.
Конверт в snake_case, а **имена метрик — в camelCase**, как в админке.
Доли — целые проценты 0–100.

| Поле | Смысл |
|---|---|
| `tasksCreated`, `completed`, `completionRate` | создано, из них выполнено, доля выполненных |
| `medianCompletionMinutes` | медиана минут от создания до выполнения |
| `slaViolationRate`, `overdueCount` | доля нарушений срока; сколько открытых просрочено сейчас |
| `byEmployee[]`, `byType[]` | то же по сотрудникам и по типам |
| `paymentRecoveryRate` | доля платёжных задач с итогом `RECOVERED` |
| `followupCompletionRate` | доля выполненных `FOLLOWUP_OVERDUE` |
| `onboardingCompletionMedianMinutes` | медиана закрытия онбординга |
| `escalationRate` | доля автозадач, дошедших до эскалации |

- Созданные и выполненные считаются по задачам, **созданным** в периоде. Просрочка,
  нарушения, восстановление оплат и эскалации — по **текущему** состоянию, включая
  более старые открытые задачи. Поэтому `overdueCount` не обязан укладываться в
  `tasksCreated` периода.
- `null` у медианы значит «в периоде нечего мерить», а не «ноль минут». Так и пиши.
- Цифры и округление те же, что в админке: отчёт сверяется с владельцем один в один.

## POST /tasks/{id}/annotations

Тело: `kind` = `recommendation` | `analysis`, `text` (1–4000), `data` — необязательный
объект с доказательствами (id сообщений, счётчики). Ответ `201 {task_id, annotation}`.
Статус, срок и ответственного задачи запись не меняет. `Idempotency-Key` работает.

```bash
curl -sS -X POST "$PUBLICIA_BASE_URL/api/service/v1/tasks/$TASK_ID/annotations" \
  -H "Authorization: Bearer $PUBLICIA_SERVICE_TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: ann-$TASK_ID-$(date +%F)" \
  -d '{"kind":"recommendation","text":"Клиент дважды спрашивал про СБП, ссылка на карту не подходит. Предложить оплату по СБП.","data":{"message_ids":["clm…"]}}'
```

**Аннотацию в интерфейсе задач пока не видно** — её читают API и журнал. Чтобы
рекомендацию прочитал человек, продублируй её заметкой в сделке (`POST /notes`) или
уведомлением ответственному (`POST /actions/notify-employee`).

`POST /notes` — старый обработчик: тело в camelCase (`dealId`, `text`),
`Idempotency-Key` молча игнорируется. Повтор после сбоя сети создаст вторую заметку —
не повторяй вслепую.
